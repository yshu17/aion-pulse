# Project Master Planner

## Назначение и вход

Планируй развитие **существующего** приложения. На входе: запрос пользователя, текущее поведение/код, `PAIR.md`, [архитектура](../../../docs/PROJECT_ARCHITECTURE.md), [проблемы](../../../docs/PROJECT_ISSUES.md) и соответствующий план. Если важное решение пользователя ещё неизвестно, формулируй блокер и независимые действия.

Перед изменением открой `git status --short` и прочитай `PAIR.md`. Claude Code остаётся Lead Developer и утверждает архитектурный контракт; Codex берёт только назначенную часть. Не перезаписывай незавершённые правки другого агента.

## Выбор плана

Используй пять существующих представлений: MASTER `docs/index.html`, Telegram `docs/telegram-bridge-plan.md`, расписание `docs/schedule-notify-plan.html`, UI/UX `UI_UX_IMPROVEMENT_PLAN.md`, карта `docs/map-poi-plan.html`. MASTER — производный обзор. Не создавай шестой основной план. Правила источников, ID, дат и сборки — в [контракте планов](references/plan-contract.md); читай его перед редактированием задач.

## Работа над планом

1. Сверь запрос с существующими ID и историей; устрани дубли по смыслу и отметь уже реализованное на основании кода, теста, отчёта или решения пользователя. Личные отметки браузера не считаются командным статусом.
2. При новой функции коротко сформулируй сценарий пользователя, ограничения клиента и сервера, входы/выходы и критерий успеха. Для неоднозначной функции проведи короткое обсуждение вариантов с пользователем, затем зафиксируй выбранный вариант.
3. Разбей работу на проверяемые задачи с зависимостями и назначенным исполнителем. Укажи критический путь, риски, блокеры, артефакт и способ проверки. Отделяй исследование данных от подключения к приложению и игровой сверки.
4. Новому пункту дай следующий постоянный ID. В исходном массиве сохрани порядок номеров; в интерфейсе новые и большие номера показываются выше. Не удаляй завершённые пункты и не ставь исторические даты задним числом. Маркер «НОВОЕ» только у последнего добавленного пункта, пока он открыт.
5. Для каждой новой открытой задачи добавь рекомендацию в `docs/plan-ai-tools.json` (поле `tasks.<ключ>`): категория → минимальный набор скиллов из реестра `skills` (основной и дополнительные, у каждого «зачем») → исполнитель `claude` / `codex` / `joint` / `user` и проверяющий → разделение «проектирование / реализация / тест / утверждение» → критерии готовности и тесты → `handoff` (`ready` — только если Codex может начать без решения Claude) и `arch_review`. Это решение Claude по содержанию задачи, не шаблон: инструмента, которого нет в реестре, не придумывай — добавь его в `skills` с честным `source`, сборка сама покажет «не найден». Порядок, ID, «НОВОЕ» и дата остаются за генератором; `python tools/check_plans.py` предупредит об открытой задаче без рекомендации. Текст для Codex: `python tools/plan_ai_tools.py codex <ключ>`, шаблон — [docs/AI_HANDOFF_TO_CODEX.md](../../../docs/AI_HANDOFF_TO_CODEX.md).
6. После каждого завершённого шага обнови его статус и заметку с конкретным свидетельством. Проверь зависимости и последствия для следующих шагов. Раздели задачи Claude и Codex по `PAIR.md`.
7. Пересобери локальные страницы и запусти проверку целостности из контракта. Запиши итог в `PAIR.md` и передай Claude. Онлайн Claude Artifact обновляет только Claude.

Применяй уже установленный Superpowers для brainstorming, writing plans и executing plans, когда задача действительно сложная. Не копируй его скиллы и не навязывай полный ритуал для мелкой правки.

## Результат и качество

Передавай: цель, текущий факт, последовательность задач, ID и зависимости, критический путь, риск/блокер, критерий готовности каждого шага, владелец, статус и ссылки на изменённые исходники. Диаграмму Mermaid используй, когда она проясняет зависимости или поток; раскрытие, поиск, фильтры, график и timeline обеспечивает существующий генератор планов. Не записывай пункт «готово» по одному утверждению без проверки.
