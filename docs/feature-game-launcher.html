Оценить и спланировать отдельный сценарий запуска игры из приложения без потери текущих функций наблюдения чата и карты.

Пользовательские сценарии
  • Игрок выбирает установленный клиент и запускает его через понятную кнопку с диагностикой ошибок.
  • После закрытия игры приложение продолжает или завершает слежение согласно явно выбранной настройке.
Функциональные требования
  • Определить официальный/разрешённый способ запуска и допустимые аргументы до реализации.
  • Отделить запуск процесса, обновление клиента и контроль файлов как разные решения.
  • Не изменять игровую папку или параметры запуска на этапе черновика; сохранять текущий прямой запуск приложения.
Неподтверждённые игровые механики и данные

Для дальнейшей проработки Claude Code
  1. Архитектурные вопросы: Оценить границы процесса, пути, обновления, конфигурации и жизненного цикла Tk.
  2. Недостающие игровые данные: Проверить официальный способ запуска и требования клиента.
  3. Необходимые исследования: Уточнить правила сервера, поддержку и совместимость с обновлятором.
  4. Варианты пользовательского интерфейса: Сравнить кнопку запуска в текущем окне и отдельный экран лаунчера.
  5. Идеи анимаций и интерактивности: Оценить состояние запуска/ожидания/ошибки без блокировки ввода.
  6. Необходимые диаграммы: Последовательность пользователь → приложение → официальный лаунчер/игра → завершение.
  7. Технические риски: Нарушение обновлений, потеря доступа, разные установки, права Windows, безопасность учётных данных.
  8. Вопросы, требующие решения владельца: Нужен только запуск игры или также обновления/авторизация; допускается ли отдельное окно?
  9. Предлагаемые следующие этапы: Утвердить границу MVP и способ запуска; античит рассматривать отдельно в DRAFT-06.
